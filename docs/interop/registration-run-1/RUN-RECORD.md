**Interop tasks B.2 (register) and B.4 (public, reproducible run).**
Executed 2026-08-30 by the maintainers' agent at the founder's
direction. Result: **registered; receipt verified by the service's own
verifier and re-verified offline from the artifacts in this directory.**
One interop finding, stated below.

Not to be confused with bridge runs **B1/B2** in
`docs/specs/pala-1/independent-runs/turak/`, which verified the *statement
construction*; this run exercises the *registration and receipt* side.

## Claim, scoped exactly

A PALA-1 Signed Statement (v2 construction, #192) was registered with the
scitt-community **reference implementation** (`scitt-api-emulator`, CCF
tree algorithm) carrying a **one-line RFC 9597 compatibility patch**
(diff in `emulator-patch.diff`), operated by ourselves on localhost for
the duration of the run, under a **single-use ephemeral key** generated
and destroyed within the run environment. The service issued a receipt
that its own verifier accepts, and that anyone can re-verify from the
files here. This demonstrates that the bridge's statement is
*registrable* and *receipt-verifiable* with a conforming reference
implementation. It does not demonstrate a third-party operator, a
production key custody, or the final RFC receipt format (see
"Limitations").

## Finding R1-F1 — the reference implementation predates RFC 9597's label

First submission, 21:45:22Z: **HTTP 400**,
`{"detail": "Claim does not have a CWTClaims header parameter",
"type": "urn:ietf:params:scitt:error:invalidInput"}`.

Root cause, pinned in code: `scitt_emulator/create_statement.py` defines
`class CWTClaims(CoseHeaderAttribute): identifier = 14` — the draft-era
label. **RFC 9597 registered CWT Claims as header label 15**, which is
what this bridge emits and what bridge runs B1 and B2 independently
confirmed against the RFC. The emulator's own statement builder still
emits 14 (and `393 => Reg_Info`, another draft-era value), and the
installed pycose (1.1.0) has no CWT-Claims header class of its own, so
label 15 decodes as a bare integer and the presence check fails.

Resolution: the statement was **not** changed — emitting a draft label to
satisfy an outdated implementation would make the bridge non-conformant
to the published RFC. The emulator, which is infrastructure here rather
than the artifact under test, received a one-line patch (`identifier =
14` → `15`); the diff is published in `emulator-patch.diff` and is part
of this run's claim. Receipt cryptography is untouched by it.

Follow-up: report upstream to scitt-community (label 14 → 15; 393).

## Reproduce

```bash
python3 -c "import pathlib; pathlib.Path('s.cose').write_bytes(bytes.fromhex(open('statement.hex').read().strip())); pathlib.Path('r.cbor').write_bytes(bytes.fromhex(open('receipt.hex').read().strip()))"
python3 -m scitt_emulator.cli client verify-receipt --claim s.cose --receipt r.cbor --service-parameters service_parameters.json
```
(emulator installed as in "Environment", patch applied). The statement's
own signature and commitment verify with `palimpsests[scitt]`:
`check_statement_against_head(bytes, Ed25519PublicKey(252a57c4…), head)`.

## Limitations, stated

- **Operator = ourselves**, on localhost, for minutes. A hosted
  third-party transparency service is the stronger class of evidence
  and is a separate, later run.
- **Ephemeral single-use key.** Production key custody is out of scope
  here and belongs to a deployment's own policy.
- **Receipt format is the emulator's draft-era CCF receipt**, not a
  final RFC receipt shape; the *statement* side is final-RFC (9052, 9597,
  9943 with `kid` and content type). Receipt verification therefore
  follows this service's protocol, as the bridge documentation already
  states it always will.
- The emulator runs Flask in debug mode by default; localhost only,
  environment destroyed after the run.
